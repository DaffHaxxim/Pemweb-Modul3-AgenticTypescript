## 1. Overview

### 1.1 What this is
A small TypeScript project that solves the seven exercises of section 16 ("Latihan TypeScript") of the Modul 3 handout stored next to it in `../Materials/README.md`. Each exercise is one source file in `src/`. A runner (`src/index.ts`) calls them all and prints the results, `tsc --noEmit` checks every type, and the `notes/` folder holds the written parts the handout asks for (a discussion for exercise 6, an error log for exercise 7) plus deliberately wrong code that proves the type-level requirements.

The seven exercises, with the file that answers each:

| # | Handout requirement | File |
|---|---|---|
| 1 | `average(nums: number[])` that handles an empty array correctly | `src/01-basic-types.ts` |
| 2 | `formatId(id: string \| number)`: upper-case strings, 6-digit numbers | `src/02-union-narrowing.ts` |
| 3 | `PaymentMethod` discriminated union and `describe()` with a `never` check | `src/03-discriminated-union.ts` |
| 4 | `ProductSummary`, `ProductUpdate` (no `id`), `ReadonlyProduct` | `src/04-utility-types.ts` |
| 5 | `groupBy<T, K extends string \| number>` | `src/05-generics.ts` |
| 6 | `fetchJson<T>` that throws on `!res.ok`, plus a discussion of what `T` does not guarantee | `src/06-async.ts`, `notes/06-async-discussion.md` |
| 7 | Convert the Modul 2 "Intermediate JavaScript" code to strict TypeScript and record the errors | `src/07-refactor/`, `notes/07-original/`, `notes/07-refactor-errors.md` |

The project has no screenshots and no GUI steps, so this guide has none.

### 1.2 Why it exists
Section 16 is the practice part of Modul 3 for the web programming lab course. The handout states the exercises but not their solutions, and several of them are only meaningful if you see the compiler reject something (the `never` check, "no `id` in an update", the strict-mode error log). The project therefore keeps two kinds of evidence side by side: code that runs (`npm start`) and code that must fail to compile (`notes/compile-errors/`), each with its recorded compiler output.

Scope rule used while writing it: only constructs the handout itself teaches or requires were used (strict TypeScript, `tsc --noEmit` as the checker, `tsx`, `if` and `instanceof` narrowing, utility types, `never`, generics, `as` only with a stated reason, `console.log` output). No test framework, no `@ts-expect-error`, and no `this` parameter tricks were added because the handout does not teach them. One deliberate exception is flagged where it occurs: `String.prototype.padStart` in exercise 2, which is plain JavaScript that the handout does not teach but the "6-digit number" requirement effectively needs.

### 1.5 Key concepts and terms
- **strict mode:** the `"strict": true` bundle of compiler checks, including `strictNullChecks` (so `null` and `undefined` are their own types) and `noImplicitAny`.
- **Narrowing:** the compiler refining a variable's type inside a branch after a check such as `typeof x === "string"` or `p.kind === "card"`.
- **Discriminated union:** a union of object types that share a literal-typed property (`kind`) whose value tells them apart.
- **`never`:** the type with no values. Assigning a leftover union member to `never` makes the compiler prove a `switch` is exhaustive.
- **Utility types:** built-in type-level functions (`Pick`, `Omit`, `Partial`, `Readonly`, `Record`) that derive new types from existing ones. They exist only at compile time.
- **Type assertion (`as`):** tells the compiler to trust a type. It changes nothing at runtime.
- **NodeNext / ESM:** with `"module": "NodeNext"` and `"type": "module"` in `package.json`, files are ES modules and relative imports must name the compiled file, so `import ... from "./01-basic-types.js"` is written with `.js` even though the source is `.ts`.
- **Type erasure:** types are removed when TypeScript compiles to JavaScript, so nothing about `T` or an interface exists at runtime.

### 3.1 Command: `npm init -y`
**Runs in:** host zsh on WSL Ubuntu, working directory `Latihan-Typescript/`, Node v24.14.0 · **Run by:** Claude (the reader would run the same command)
```bash
npm init -y
```
**Function**
1. Creates `package.json` in the current folder with default values (name taken from the folder, version `1.0.0`, a placeholder `test` script, `"type": "commonjs"`). It prints the generated file and changes nothing else.
2. Every later step depends on this file: `npm install` records dependencies in it and `npm run <name>` reads its `scripts`. The generated defaults were not kept as is: `"type"` had to become `"module"` and the scripts were replaced (see 3.5).

**Mechanism**
- `-y` (`--yes`) answers every question of the interactive `npm init` wizard with its default, so the command is non-interactive.
- npm derives `name` from the directory name, lower-cased and validated against npm's naming rules, which is why the folder `Latihan-Typescript` became `latihan-typescript`.
- Failure mode: if a `package.json` already exists, `npm init -y` keeps the existing fields and only fills in missing ones, so it does not overwrite an existing project.

### 3.2 Command: `npm install --save-dev typescript @types/node tsx`
**Runs in:** host zsh on WSL Ubuntu, `Latihan-Typescript/` · **Run by:** Claude
```bash
npm install --save-dev typescript @types/node tsx
```
```text
added 7 packages, and audited 8 packages in 6s

found 0 vulnerabilities
```
**Function**
1. Downloads three packages and their dependencies into `node_modules/`, writes them into `devDependencies` in `package.json`, and creates `package-lock.json` with the exact resolved versions (7 packages added in total).
2. `typescript` provides the `tsc` compiler used by every script. `@types/node` provides the type declarations for Node's built-in APIs (`console`, `process`, `fetch` globals). `tsx` is a runner that executes `.ts` files directly, used only by `npm run dev` (3.29). The handout's section 2 names the first two; `tsx` is added for the run method in section 14.
3. Without `typescript` no script works; without `@types/node` the Node-specific names in compiled code would be unknown to the checker; without `tsx` only `npm run dev` fails.

**Mechanism**
- `--save-dev` (`-D`) records each package under `devDependencies` instead of `dependencies`: they are needed to build and run during development, not by a consumer of the package.
- Version ranges are written with a caret (`^7.0.2`), meaning any compatible release up to the next major version. Because no version was given, npm resolved the newest published one, which is how TypeScript 7.0.2 (the native compiler generation) was installed. The exact versions are frozen in `package-lock.json`.
- npm places executables of installed packages in `node_modules/.bin/`, and `npm run` and `npx` put that folder on the `PATH`, which is why `tsc` works without a global install (it was not installed globally on this machine).
- Failure modes: no network gives an `ENOTFOUND`/`EAI_AGAIN` error and no changes; a Node version older than the packages' `engines` field prints an `EBADENGINE` warning.

### 3.5 File: `package.json`
**Role:** the project manifest. `npm` reads it for scripts and dependencies, and Node reads its `"type"` field to decide how to load every `.js` file in the project. **Structure:** metadata (lines 2-4), module mode (5), scripts (6-11), license (12), dev dependencies (13-17).

#### 3.5.1 Module mode and scripts (lines 5-11)
```json
  "type": "module",
  "scripts": {
    "build": "tsc",
    "typecheck": "tsc --noEmit",
    "start": "node dist/index.js",
    "dev": "tsx src/index.ts"
  },
```
**Function**
1. `"type": "module"` makes Node treat the compiled `.js` files as ES modules, so `import`/`export` and top-level `await` work in `dist/index.js` and `src/index.ts` runs through `tsx`.
2. The five scripts are the project's whole command surface: `build` compiles `src/` into `dist/`, `typecheck` checks without writing files, `start` runs the compiled runner, and `dev` runs the TypeScript runner directly. The first three are the scripts section 2 of the handout asks for; `dev` adds the `tsx` method from section 14.
3. The runner's top-level `await` (for exercise 6) only compiles because the module system is ES modules; switching `"type"` back to `commonjs` would make `tsc` reject it.

**Mechanism**
1. `npm run <name>` looks the name up in `scripts`, prepends `node_modules/.bin` to `PATH`, and runs the string in a shell. `npm start` is a built-in alias for `npm run start`.
2. `tsc` with no file arguments finds `tsconfig.json` in the current folder (or a parent) and compiles what its `include` lists. `tsc --noEmit` performs the same checking but skips writing output.
3. `node dist/index.js` loads the compiled file. Because of `"type": "module"`, Node resolves its `import ... from "./01-basic-types.js"` lines as ES module specifiers, which need the explicit `.js` extension (see 3.6).
4. `tsx src/index.ts` strips the types with a fast transpiler and runs the result. It does not type-check, which is why `typecheck` is a separate script.
- **Edge cases and failure modes:** `npm start` before `npm run build` fails with `Cannot find module .../dist/index.js`. With `"type": "module"`, a relative import written without an extension would fail at runtime in Node even though some type checkers accept it.

#### 3.5.2 Dependencies (lines 13-17)
```json
  "devDependencies": {
    "@types/node": "^26.6.4",
    "tsx": "^4.23.15",
    "typescript": "^7.0.2"
  }
```
**Function:** lists the three development packages and the allowed version ranges. `npm install` (no arguments) in a fresh clone reinstalls exactly these, with versions pinned by `package-lock.json`. `typescript` at `^7.0.2` means the compiler generation described in 3.32 and 3.33, whose command-line behavior differs from older versions.
**Mechanism:** a caret range `^X.Y.Z` accepts `>=X.Y.Z <(X+1).0.0`. The lock file, not these ranges, decides what a clean install actually fetches.

### 3.6 File: `tsconfig.json`
**Role:** the compiler settings used by `tsc` (and `npm run build`, `npm run typecheck`). It is the handout's recommended configuration for learning and new projects, unchanged, and it is also the base that `notes/tsconfig.json` extends (3.17). **Structure:** `compilerOptions` (lines 2-11), `include` (12).

#### 3.6.1 `compilerOptions` and `include` (lines 1-13)
```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```
**Function**
1. Decides what is checked (`include: ["src"]`), how it is checked (`strict`, `noUncheckedIndexedAccess`), what is produced (ES2022 JavaScript into `dist/`), and how imports are resolved (`NodeNext`).
2. Every exercise depends on `strict`. The `number | null` return type of `average`, the `if (bucket)` check in `groupBy` and the `never` check in `describe` are all meaningful only because null checks are on. `noUncheckedIndexedAccess` is why `divs[i]` in `src/07-refactor/dom.ts` needs a check and why the original DOM loop produced an error (3.19).

**Mechanism**

| Option | Value | What it does here |
|---|---|---|
| `target` | `ES2022` | Output uses modern syntax unchanged (classes, `??`, top-level `await`). Also selects the default type libraries, which include DOM, which is why `document` type-checks in `dom.ts`. |
| `module` / `moduleResolution` | `NodeNext` | Follows Node's real ESM rules: file type comes from `package.json` `"type"`, relative imports need the compiled file extension (`./x.js`), and TypeScript maps `./x.js` back to `x.ts` while checking. |
| `rootDir` / `outDir` | `src` / `dist` | `src/index.ts` becomes `dist/index.js`, keeping the folder structure. |
| `strict` | `true` | Turns on `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes` and the rest of the strict family. |
| `noUncheckedIndexedAccess` | `true` | Reading `arr[i]` or an index-signature property yields `T \| undefined`. Verified in a scratch experiment: `const first: number = arr[0]` fails with TS2322 (`number | undefined` is not assignable to `number`). |
| `skipLibCheck` | `true` | Skips checking `.d.ts` files of dependencies, which speeds up compilation and avoids errors that are not in this project's code. |

- **Under the hood:** `include` paths are relative to the folder containing the config file, and `rootDir` must contain every input file, otherwise `tsc` reports TS6059. That rule is why `notes/tsconfig.json` overrides `rootDir` (3.17).
- **Edge cases and failure modes:** removing `"include"` makes `tsc` compile every `.ts` file under the folder, including the deliberately failing ones in `notes/`, so `npm run typecheck` would fail. Setting `"strict": false` makes the compile-error demos in 3.20 to 3.22 stop failing, which silently removes the evidence for the requirements.

### 3.8 File: `src/01-basic-types.ts`
**Role:** exercise 1. One exported function with no side effects; imported by `src/index.ts` (3.16) and by `notes/compile-errors/ex1-ex2-ex5-calls.ts` (3.20). **Structure:** explaining comment (1-4), the function (5-10).

#### 3.8.1 `average` (lines 1-10)
```ts
// Exercise 1 - Basic types.
// An empty array has no mean. Returning 0 would claim "the average is zero" and NaN
// silently poisons later arithmetic, so the honest return type is `number | null`.
// Callers must handle null (enforced by strictNullChecks).
export function average(nums: number[]): number | null {
  if (nums.length === 0) return null;
  let sum = 0;
  for (const n of nums) sum += n;
  return sum / nums.length;
}
```
**Function**
1. Takes an array of numbers and returns their arithmetic mean, or `null` when the array is empty. It reads its argument and changes nothing.
2. The return type `number | null` is the answer to the handout's hint "pikirkan tipe return yang tepat". `0` would claim the mean of nothing is zero, and `NaN` (what `0 / 0` produces) would stay a `number`, flow silently into later arithmetic and spread. With `null` in the type, strict mode forces every caller to decide what an empty list means. `notes/compile-errors/ex1-ex2-ex5-calls.ts` (3.20) proves it: `const mean: number = average([1, 2, 3])` fails with TS2322, `Type 'number | null' is not assignable to type 'number'`.
3. Nothing else in `src/` calls it; only the runner prints its results (`2.5` for `[1, 2, 3, 4]`, `null` for `[]`).

**Mechanism**
1. Line 6 guards the empty case first, so line 9 never divides by zero.
2. `for (const n of nums) sum += n;` iterates the array values with the iterator protocol, and `sum` is inferred as `number` from its initializer `0` (type inference, handout section 3.2).
3. The loop is written with `for...of` instead of `nums[i]` on purpose: with `noUncheckedIndexedAccess` on, `nums[i]` would be `number | undefined` and would need a check on every access.
- **Under the hood:** numbers are IEEE 754 doubles, so results carry floating-point rounding (`0.1` and `0.2` average to `0.15000000000000002`); `NaN` or `Infinity` inside the array propagate to the result unchanged.
- **Edge cases and failure modes:** the type says nothing about `NaN` elements; they pass type checking and produce `NaN` at runtime.

### 3.9 File: `src/02-union-narrowing.ts`
**Role:** exercise 2. A function over a union type. **Structure:** comment (1-3), the function (4-9).

#### 3.9.1 `formatId` (lines 1-9)
```ts
// Exercise 2 - Union + narrowing.
// `typeof id === "string"` narrows the union: in the if-branch `id` is string,
// afterwards TypeScript knows it can only be number.
export function formatId(id: string | number): string {
  if (typeof id === "string") {
    return id.toUpperCase();
  }
  return String(id).padStart(6, "0");
}
```
**Function**
1. Returns an upper-cased string when given a string and a 6-digit zero-padded string when given a number: `formatId("ab-12")` gives `AB-12`, `formatId(482)` gives `000482`.
2. It is a pure function. The runner prints both results, and `notes/compile-errors/ex1-ex2-ex5-calls.ts` (3.20) shows `formatId(true)` rejected with TS2345, because the parameter type admits only `string | number`.

**Mechanism**
1. The parameter type `string | number` is a union. On line 5, `typeof id === "string"` is a narrowing check: inside the `if`, TypeScript knows `id` is `string`, so `toUpperCase()` is allowed (it does not exist on `number`).
2. Because the `if` branch returns, control-flow analysis concludes that after it `id` can only be `number`, so line 8 needs no second check.
3. `String(id)` converts the number to its decimal text and `padStart(6, "0")` adds `0` characters on the left until the text is 6 characters long.
- **Scope note:** `padStart` is a standard JavaScript method that the Modul 3 handout does not teach. It is used because the exercise's "6 digit" requirement is exactly left padding.
- **Edge cases (observed by running the compiled file):** numbers of seven or more digits are not truncated (`formatId(1234567)` is `1234567`); a negative number pads around the sign (`formatId(-5)` is `0000-5`); a fraction keeps its dot (`formatId(4.5)` is `0004.5`); `NaN` becomes `000NaN`. The exercise does not define these cases, and the types do not exclude them.

### 3.10 File: `src/03-discriminated-union.ts`
**Role:** exercise 3. A discriminated union and a function that must handle every member. **Structure:** the type (4-7), `describe` (9-24).

#### 3.10.1 `PaymentMethod` (lines 1-7)
```ts
// Exercise 3 - Discriminated union with an exhaustiveness check.
// The shared literal property `kind` is the discriminant: checking it narrows
// the whole object to one variant.
export type PaymentMethod =
  | { kind: "card"; brand: string; last4: string }
  | { kind: "transfer"; bank: string; accountNo: string }
  | { kind: "cash"; amount: number };
```
**Function**
1. Defines three payment shapes that differ in their fields: a card has `brand` and `last4`, a transfer has `bank` and `accountNo`, cash has `amount`. The field `kind`, a string literal type in each member, says which shape a value is.
2. Any function taking a `PaymentMethod` can read only `kind` until it checks it, and then gets exactly the fields of that variant. Creating a value with a wrong combination (for example `{ kind: "cash" }` without `amount`) is a compile error.

**Mechanism**
- Each union member is an object type; the literal types `"card"`, `"transfer"`, `"cash"` make `kind` a discriminant. When code compares `p.kind` to one of those literals, TypeScript removes the members that cannot match, so `p` is narrowed to a single member.
- The type is erased at compile time: at runtime a `PaymentMethod` is an ordinary object with a `kind` string property.

#### 3.10.2 `describe` and the `never` check (lines 9-24)
```ts
export function describe(p: PaymentMethod): string {
  switch (p.kind) {
    case "card":
      return `Card ${p.brand} ending in ${p.last4}`;
    case "transfer":
      return `Bank transfer via ${p.bank} (account ${p.accountNo})`;
    case "cash":
      return `Cash payment of ${p.amount}`;
    default: {
      // If a new variant is added to PaymentMethod and not handled above,
      // `p` is no longer `never` here and this assignment fails to compile.
      const _exhaustive: never = p;
      return _exhaustive;
    }
  }
}
```
**Function**
1. Turns any payment into a sentence: `Card Visa ending in 4242`, `Bank transfer via BCA (account 1234567890)`, `Cash payment of 50000`. Pure function.
2. The `default` branch is a compile-time safety net, not behavior. If someone later adds a fourth member to `PaymentMethod` and forgets this `switch`, the assignment on line 20 stops compiling. `notes/compile-errors/ex3-never.ts` (3.21) reproduces that situation and records the error: `Type '{ kind: "crypto"; coin: string; }' is not assignable to type 'never'` (TS2322).

**Mechanism**
1. `switch (p.kind)` narrows `p` in each `case` to one member, so `p.brand`, `p.bank` and `p.amount` are available only where they exist.
2. After all three cases, every member has been handled, so TypeScript narrows `p` in `default` to `never`, the type with no values. Assigning `p` to a variable annotated `never` (line 20) compiles only when `p` really is `never`. Returning `_exhaustive` is allowed because `never` is assignable to `string`.
- **Edge cases and failure modes:** the check is compile-time only. If a value that does not match the type reaches the function at runtime (for example JSON parsed with `as PaymentMethod` and an unknown `kind`), the `default` branch runs and returns that object itself, not a string.

#### 3.11.1 `Product` and the three derived types (lines 1-16)

**Function**

### 3.12 File: `src/05-generics.ts`
**Role:** exercise 5. A generic grouping function. **Structure:** comment (1-4), the function (5-23).

#### 3.12.1 `groupBy` (lines 1-23)
```ts
// Exercise 5 - Generics.
// T is the item type, K is whatever key the callback produces. The constraint
// `K extends string | number` is required because Record<K, ...> only accepts
// keys that are valid property names.
export function groupBy<T, K extends string | number>(
  items: T[],
  key: (item: T) => K,
): Record<K, T[]> {
  // Built as Partial because the object starts empty and keys appear one by one.
  const result: Partial<Record<K, T[]>> = {};
  for (const item of items) {
    const k = key(item);
    const bucket = result[k];
    if (bucket) {
      bucket.push(item);
    } else {
      result[k] = [item];
    }
  }
  // Boundary assertion: every key that exists was filled, but TypeScript cannot
  // prove that for an open key type K, so the Partial is narrowed back once, here.
  return result as Record<K, T[]>;
}
```
**Function**
1. Splits an array into buckets keyed by what the callback returns: `groupBy(words, (w) => w.charAt(0))` returns `{ a: ["apple", "avocado"], b: [...], c: ["cherry"] }`. It does not modify the input, and items keep their original order within a bucket.
2. Its type signature does the exercise's real work: `K` is inferred from the callback, so the result type is `Record<K, T[]>` with the exact key type (`Record<number, string[]>` for the length example, and for a callback returning `"many"` or `"few"` literals the compiler knows only those two keys exist). The runner uses it with number keys and with string keys.
3. Only the runner and `notes/compile-errors/ex1-ex2-ex5-calls.ts` (3.20) call it. The latter shows `groupBy([1, 2, 3], (n) => n > 1)` rejected with TS2322, because `boolean` does not satisfy `string | number`.

**Mechanism**
1. `T` and `K` are type parameters, chosen by inference at each call. `K extends string | number` is a constraint: `Record<K, ...>` is only valid for key types that can be property names, and the constraint tells the compiler `K` always qualifies.
2. The accumulator is declared `Partial<Record<K, T[]>>` because it starts empty. Reading `result[k]` therefore gives `T[] | undefined`. A scratch experiment confirmed that skipping the check and calling `.push` directly fails with TS18048 (`'bucket' is possibly 'undefined'`), which is why lines 14 to 18 branch.
3. Line 22 is the one `as` in the project. The compiler cannot prove that the `Partial` object contains every key of an open type `K` (the same experiment showed that returning it without `as` fails with TS2322, `Partial<Record<K, T[]>>` is not assignable to `Record<K, T[]>`), so the cast is placed once, at the boundary, with the comment on lines 20 and 21 giving the reason.
- **Under the hood:** JavaScript object keys are strings. A number key such as `5` becomes `"5"`, and integer-like keys are enumerated in ascending numeric order regardless of insertion order. The observed output for word lengths lists `5, 6, 7, 9` although `avocado` (7) was inserted before `banana` (6).
- **Edge cases and failure modes (observed):** keys that collide with properties inherited from `Object.prototype` crash the function. `groupBy(["toString"], (w) => w)` throws `TypeError: bucket.push is not a function`, because `result["toString"]` finds the inherited function (truthy) instead of `undefined`. `groupBy(["__proto__"], (w) => w)` throws the same error for the same reason. A prototype-free accumulator (`Object.create(null)`) or a `Map` would avoid this; the exercise's required return type `Record<K, T[]>` is why a plain object is used.

**Role:** exercise 6. A typed wrapper around `fetch`. **Structure:** comment (1-8), the function (9-15).

#### 3.13.1 `fetchJson` (lines 1-15)
```ts
// Exercise 6 - Async.
// `res.ok` is false for any status outside 200-299 (fetch only rejects on network
// failure), so it must be checked explicitly and turned into an Error.
//
// Discussion: `T` is a promise to the compiler, not a check at runtime.
// `res.json()` returns `Promise<any>`, and `any` is assignable to any `T`, so the
// call below type-checks whatever the server really sends. See
// notes/06-async-discussion.md for a demonstration.
export async function fetchJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) {
    throw new Error(`Request to ${url} failed: ${res.status} ${res.statusText}`);
  }
  return (await res.json()) as T;
}
```
**Function**
1. Requests a URL, converts HTTP error statuses into a thrown `Error`, and otherwise returns the parsed JSON body typed as `T`. It makes one network request (or reads a `data:` URL) and changes no local state.
2. Callers choose the type: `fetchJson<User>(url)`. The runner calls it three times (3.16): a valid `data:` URL, a `data:` URL whose body has the wrong shape, and a real request that returns HTTP 404, which produces `Gagal: Request to https://jsonplaceholder.typicode.com/users/9999 failed: 404 Not Found`.
3. The handout's discussion question ("apa yang *tidak* dijamin oleh `T`") is answered in `notes/06-async-discussion.md` (3.23) and demonstrated by the wrong-shape call.

**Mechanism**
1. `fetch(url)` resolves its promise for any HTTP response, including 404 and 500; it rejects (with a `TypeError`) only when the request itself fails (DNS error, connection refused). Hence the explicit check.
2. `res.ok` is `true` exactly for status codes 200 to 299. Otherwise the function throws an `Error` that carries the URL, status code and status text; the `async` function turns the throw into a rejected promise.
3. `res.json()` reads the whole body and parses it as JSON. Its declared return type is `Promise<any>` (a scratch experiment confirmed `const n: number = await res.json()` compiles), and `any` is assignable to every type, so `as T` is not even needed to compile; it documents the assumption.
4. The `as T` assertion (module section 12 uses the same one) has no runtime effect. The types `T` and `User` do not exist after compilation, so nothing compares the body with them.
- **Edge cases and failure modes:** a body that is not valid JSON makes `res.json()` reject with a `SyntaxError`; a JSON body of the wrong shape passes through silently (shown in 3.28); a network failure rejects with `TypeError: fetch failed`, which is not covered by the `!res.ok` branch.

## 4. End-to-end walkthrough

One complete pass from an empty folder to a verified solution, following the real order of the session:

1. **Create the project (3.1 to 3.4).** `npm init -y` makes `package.json`; `npm install --save-dev typescript @types/node tsx` adds the toolchain and the lock file; `npx tsc --init` makes a starter `tsconfig.json`; `mkdir` creates the source folders.
2. **Set the rules (3.5 to 3.7).** `package.json` is rewritten with `"type": "module"` and the five scripts; `tsconfig.json` is replaced by the handout's strict configuration (ES2022, NodeNext, `strict`, `noUncheckedIndexedAccess`); `.gitignore` excludes the generated folders.
3. **Write the exercises (3.8 to 3.15).** Exercises 1 to 6 are one function or type group each. Exercise 7 starts from the verbatim Modul 2 code (3.18, 3.19): it is checked first with `npx tsc -p notes` (3.31), which yields zero errors for the arrays and objects and 15 for the DOM code, and the refactor (`fruits.ts`, `dom.ts`) answers those errors one by one.
4. **Add the runner (3.16).** `src/index.ts` calls each exercise with sample data and prints a labelled result.
5. **Prove the type-level requirements (3.20 to 3.22).** Wrong calls and a missing `switch` case are written on purpose in `notes/compile-errors/`, and `npx tsc -p notes` shows the exact diagnostics.
6. **Verify.** `npm run typecheck` (3.26) exits 0, `npm run build` (3.27) writes `dist/`, `npm start` (3.28) prints every result including a real HTTP 404 turned into an `Error`, `npm run dev` (3.29) and `bun src/index.ts` (3.30) give the same values, and the one-file compile is checked in a scratch copy (3.32) and shown to be rejected inside the project (3.33).
7. **Write the evidence down.** `notes/06-async-discussion.md` (3.23) and `notes/07-refactor-errors.md` (3.24) hold the prose the handout asks for, and `README.md` (3.25) maps every requirement to the command or file that proved it.

A single value traced through the code: `formatId(482)` enters `src/index.ts` (3.16.2), is checked against `string | number` at compile time, takes the second branch of `formatId` (3.9.1) because `typeof 482 === "string"` is false, becomes `"482"`, is padded to `"000482"`, and is printed by `console.log` as `formatId(482)     = 000482` (3.28).

## 5. Pitfalls and failure modes

- **`npm run dev` and `bun` do not type-check.** A project can run fine under them and still fail `npm run typecheck`. Always run the check (3.29).
- **`npx tsc <file>` does not work with a `tsconfig.json` present in TypeScript 7.** Either use a scratch copy, pass `--ignoreConfig`, or point `-p` at a config (3.17, 3.32, 3.33).
- **`npx tsc -p notes` exits 1 by design.** Do not wire it into automation as a pass/fail gate; its non-zero exit and its 22 diagnostics are the expected state.
- **`rootDir` must contain every checked file.** Overriding `include` without also overriding `rootDir` (as in `notes/tsconfig.json`) produces TS6059 instead of the real diagnostics (3.17).
- **Types are not runtime checks.** `fetchJson<User>` returned an object without `name` and the compiler believed `string` (3.13, 3.28). The same applies to `as` anywhere in the project.
- **`groupBy` breaks on keys that exist on `Object.prototype`** (`toString`, `__proto__`) with `TypeError: bucket.push is not a function` (3.12). Fine for the exercise's data, not for arbitrary user text.
- **`ProductUpdate` allows `undefined` values**, which overwrite fields through spread in `applyUpdate` (3.11).
- **The 404 demo in `npm start` needs internet.** The two `data:` URL demos do not (3.16.4).
- **Keep to what the handout teaches.** The project deliberately has no test framework and no `@ts-expect-error`; the compiler's output on `notes/` is the evidence instead (3.4, 3.31). Adding such tools would go beyond the module's scope.
